## 讨论：给 git-diff-viewer 加「AI 解释 + 目录/文件解释映射」（仅方案，未改代码）

用户诉求：代码侧加 AI 解释入口，但网页自身不接 AI，想复用外部 AI 工具或 WorkBuddy；解释生成后自动建立
「项目目录 ↔ 当前文件」的关联映射，之后可直接回看解释。

我的判断结论（供后续推进参考）：

- **方向合理，但有一处硬伤**：本项目定位是「零依赖、无安装、只读本地 git、只在可信内网」。服务端直接接云端
  LLM 会同时打破零依赖 + 不出网 + 密钥落盘三条。主张「旁路架构」：解释模块与 diff 主链路完全隔离，失败静默降级。
- **那个「映射」概念模糊，需用户拍板是三选一**：① 文件/目录 → 解释内容的索引表；② 文件间引用依赖图（成本高，
  价值不同）；③ 目录级逐层导读。判断他实际要的是 ①+③。
- **缓存必须以内容哈希为键**（git blob hash 天然内容寻址、跨机器一致），不能用路径做键，否则旧解释误导人比没解释更糟。
- 两种解释必须分开存：解释「这次提交改了什么」≠ 解释「这个文件是干什么的」。
- 粒度必须懒加载；明确不建议全库预生成（几千文件 × 调用成本，绝大多数没人看）。
- 待用户决定的产品问题：解释是**私有笔记**（放 .gdv/ 并写 .git/info/exclude，复用已有 opIgnore）还是**团队资产**
  （入库共享）。这直接决定存储位置，未定。
- 可复用的既有能力：server.js 的 opIgnore 写 exclude、readBlob/readTree 读内容与目录、git 内容哈希。

## 补充：UI 闭环与 WorkBuddy 触发方式（用户已明确交互要求）

用户要求：点击文件树文件时，有解释文档 → 显示「看解释」按钮；没有 → 显示「去解释」；解释成功后即可查看。

- 按钮五态：无文档=「去解释」／已请求=「解释中…」禁用／有文档 hash 一致=「看解释」／hash 不一致=「看解释」+黄点「可能过期」／失败=「重试解释」。
- 文件树上额外挂状态小点（实心=已解释，空心黄=过期），不用点开就知道哪有货。
- 闭环靠状态文件，不靠进程间通信：网页 `POST /api/explain-request` 写 `.gdv/requests/<id>.json`；前端轮询
  `GET /api/explain-status`；WorkBuddy 在对话里被叫一句「处理待办」后读 requests、生成文档、原子更新
  `.gdv/explain/index.json` 并把 request 标 done；前端轮询到 done 后按钮自动变「看解释」。
- **顺序纪律**：必须先把文档写完、再更新 index.json、最后标 request done，反了会出现「按钮变了但文档没有」。
- 可复用点（实测确认）：`readFileText()` 能读 `.gdv/**`（只拦了 `.git`），现有 markdown 渲染 `renderMdPreview()`
  可直接渲染解释文档，`opIgnore()` 可把 `.gdv/` 写进 `.git/info/exclude`。新增接口只需 2 个。
- 已知缺陷需处理：WorkBuddy 未运行或用户忘了说 → request 永久 pending，按钮卡在「解释中…」，需 TTL + 取消。
- 依然未解决：局域网/服务器部署下 WorkBuddy 无法服务他人；要做到「点一下秒出」只能服务端接 LLM API（打破零依赖与不出网）。

用户要求：「逐段对照文档，直接拿着源码对照加注释」→「把源码复制一份，再源码上解释每段意思。然后关联」。

## 文档形态再升级：v2（代码块内注释）→ v3（源码分段 + 中文讲解）

用户反馈：「格式不算好看，我希望类似看源码这种效果，仅仅是加了理解的源码……可以不用注释的格式也行。
其它的附加注释事项统一放在尾部文字描述就行。」

**根因（重要，别再犯）**：v2 的 `//` 注释活在 `<pre class="md-code">` 里，而 `.md-view .md-code code`
是 `white-space: pre` + `overflow: auto` ⇒ 中文注释**不换行**，一长就横向滚动；注释和代码同色同字体，
通篇是一坨。**任何「大段中文」都不该写进代码块**，这是本项目写解释文档的硬约束。

**另一处白做工**：v2 文档头那行 `> blob … · commit … · 生成于 …` **完全没用**。前端 `renderExplainDoc`
是用 `index.json` 的 `entry.blob/commit/generatedAt` 自己渲染 `.explain-meta` 的，过期判定走
`explainKindOf` → 状态接口比对 blob，**不解析文档正文**。所以文档里再写一遍＝首屏重复三行。
v3 改成：正文不写元信息，只在文末一行小字交代，供脱离页面单独阅读时溯源。

**v3 形态**（今后标准）：正文 = 源码按行号区间切成若干段，每段一个 `#### \`L12–34\` · 段落名` 标题
+ 2–4 段讲解（正文层，14px 无衬线、正常换行、支持行内代码/加粗/列表/表格）+ 该段源码原样代码块；
**所有附加信息（位置/关联文件/可疑点/已核实的疑问）统一放尾部**。行号用行内代码包起来，
渲染后是等宽小胶囊，像源码的行号栏。

**实现方式（关键，必须沿用）**：
1. 生成器 `D:/install/git-diff-viewer/.gdv/_gen_v3.js`（已复制到工具目录，任意仓库可用；
   n06liquidglass 里也有一份）。用法 `node <gen> .gdv/_spec_xxx.js`。
2. 每个文件写一份 spec（`.gdv/_spec_<name>.js`）：`{src, out, blob, commit, title, summary[], segments[{from,to,title,prose[]}], tail[]}`。
3. 生成器做三件事：**校验分段无缝铺满 [1..N]**（`to + 1 === next.from`，空白行也要归属到某段）、
   按区间切源码、**拼完把所有 ```java 块按顺序拼回去与源文件逐行比对**，必须 `保真: PASS`。
   它会把各段末尾空行掐出代码块（避免框内多空白），但自检时把这部分空行也算进去，所以比对仍然严格。
4. spec 里的 prose 数组是按「段」拼的（`join('\n\n')`）。**代码围栏必须整块写成一项**
   （'```text\n…\n```'），拆成多个数组项会在框内混进空行。

**本次产出（n06liquidglass 仓库）**：
`GlassButton.java.md` 144 行/13 段/17.4KB、`GlassBackdrop.java.md` 271 行/15 段/23.5KB、
`GlassController.java.md` 284 行/16 段/24KB，全部 `保真 PASS`，`git status --short java/` 干净。

注意 `server.js` 改了但**进程没重启**，所以新请求文件里 `template` 还会写 `v2` —— 只是元数据，不影响实际格式。

## 修 bug：编辑视图与非编辑视图内容不一致

用户截图对比：同一个 `Android.bp`，非编辑视图 17 行（停在 `srcs` 后闭括号），编辑器 30 行（含 prize 块与 filegroup）。

## 新功能：预览滚到哪，点「编辑」就定位到哪一行

需求原话：「可以实现预览到哪里 点击编辑时候自动定位到预览位置吗」。

- `captureBrowseAnchor()`：从只读视图取锚点。用 `.fv-gutter` 的**实际行高**（`getComputedStyle().lineHeight`）
  换算 `line = floor(body.scrollTop / lh) + 1`，并记下 `offset = scrollTop - (line-1)*lh`（滚到半行时的余量）。
  有行号柱才能精确映射；markdown 预览没有行号柱 ⇒ 返回 null（排版正文和源码行号本来对不上）。
- `applyEditorAnchor()`：进编辑器后还原 —— 光标放到该行行首，`scrollTop = (line-1)*lh + offset`。
  **符号是加不是减**：offset 是「该行顶端距视口顶部」的余量，减掉会反向偏移一行。
- 抓取时机在 `enterEdit` 的 `await api('file')` **之前**（await 之后 DOM 可能已被别的渲染覆盖）；
  锚点存 `state.editAnchor`，`applyEditorAnchor` 消费一次即清空，`resetEditState` 也清。
- `focus({ preventScroll: true })`：否则 focus 先把光标滚进来、再被 scrollTop 覆盖，会闪一下。
- 自动换行模式（`state.wrap`）下行号柱不折行、代码折行，两者高度对不上 ⇒ 退化成按滚动比例定位（`ratio`），不猜光标。
- **反向（2026-10-24 追加）**：取消 / 保存退出编辑器后也要回到原行。四个函数拆成两个方向：
  `captureBrowseAnchor` → `applyEditorAnchor`（预览→编辑），`captureEditorAnchor` → `applyBrowseAnchor`（编辑→预览）；
  共用的数学抽成 `anchorFrom()` / `scrollTopOf()` / `lineHeightOf()` / `paddingTopOf()`。
- **padding 必须补偿**：`.ed-area` 有 `padding-top: 8px`，只读视图没有。不补偿的话两个方向各偏 8px，
  来回一次会「漂」——`capture` 里减掉 `paddingTop`，`apply` 里加回目标元素的 `paddingTop`。
  这组换算可逆：preview `S` → editor `S+8` → preview `S`。
- 应用时机：`applyBrowseAnchor()` 放在 `renderBrowseFile` 里**内容 innerHTML 之后**（不是之前）。
  `refreshWorking()` 之后还会把旧的 `diffTop` 写回 body，但那时内容还没到（fetch 未返回），clamp 成 0 后
  才会被锚点覆盖，所以顺序安全。
- **未做**：切换文件 / 切页丢弃编辑时不做锚点（本来就要离开这个文件）。
